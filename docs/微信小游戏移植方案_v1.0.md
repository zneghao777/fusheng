# 浮生 · 纸片屋 — 微信小游戏移植方案 v1.0

> 基于 `game/index.html` v4.1（4776 行）现状编写。
> 目标：在保留 Web 版持续迭代的前提下，增加微信小游戏版本，共用一套核心逻辑、内容数据与存档格式。

---

## 0. 结论先行

1. **平台**：走**微信小游戏**类目，不做普通小程序，也不建议 web-view 套壳。微信的类目体系里，带游戏玩法的内容属于「小游戏」，普通小程序上架游戏内容有被驳回或下架的风险。
2. **引擎**：**不引入 Cocos / Unity / Laya**。现有渲染已经是原生 Canvas 2D，换引擎意味着把 22 个绘制函数、房屋几何、人物建模全部重写；加一层平台适配层的成本低一个数量级。
3. **复用**：模拟逻辑、绘制函数、内容数据约 3000+ 行可复用；需要重写的是 HUD、12 个界面、toast、输入、存储与生命周期，约 1500–2000 行。
4. **维护**：monorepo，`core / render / ui / platform` 四层 + `web / minigame` 两个壳；内容与存档 schema 单一来源，不做 fork。
5. **存档**：本地优先、云端只做备份与迁移。按现有字段实测单档约 **1.9KB**，3 档约 6KB，容量完全不是问题；真正的约束是**云调用次数**和**审核节奏**。Web 与小游戏之间用「云同步码」或「剪贴板存档码」迁移。

**前置假设**（若与实际情况不符，见对应章节的调整说明）：

- 个人或小团队开发，短期以免费、无内购版本为主；
- Web 版继续作为主要迭代环境，小游戏版是分发渠道；
- 可以接受重写 UI 层，但不接受重写模拟与绘制逻辑。

## 1. 先厘清：你说的「小程序版」在微信里叫「小游戏」

这不是抠字眼，它直接决定代码怎么写、能不能上线。

| 维度 | 普通小程序 | 微信小游戏 |
|---|---|---|
| 入口 | 小程序 | 小游戏 |
| 视图层 | WXML + WXSS | **只有 Canvas**，没有 DOM、没有 WXML |
| 代码入口 | `app.js` + 页面 | `game.js` + `game.json` |
| 游戏内容 | 平台规范不允许 | 正确类目 |
| `web-view` | 支持（限非个人主体） | **不支持** |
| 支付 | 普通微信支付 | 虚拟支付（需版号） |
| 包体 | 主包 2MB / 分包总计 30MB | **主包 4MB / 总 30MB** |
| 本地缓存 | 10MB / 单 key 1MB | **10MB / 单 key 1MB** |

结论：这款游戏应注册为**小游戏**。下文所说的「小程序版」均指小游戏版；如果你确实要普通小程序，见 2.2 的例外路径与风险。

### 2.2 移植面量化

| 类别 | 规模 | 处理方式 |
|---|---|---|
| 模拟逻辑：`update*`、时间、需求、事件、关系、任务、经济 | 约 2000–2500 行 | **原样复用**，只去掉对全局 DOM 的隐式依赖 |
| 绘制：22 个 `draw*` + 房屋几何 + 人物三档建模 | 约 800–1000 行 | **原样复用**，把全局 `G` 改为显式传入 `ctx` |
| 内容数据 | 约 300–500 行 | **原样复用**，抽到 `content/` |
| HUD + 12 个界面 + toast | 约 900–1200 行 | **重写**为 Canvas UI |
| 输入 + 存储 + 生命周期 + 错误处理 | 约 300–400 行 | **重写**为平台适配层 |
| 构建与工程 | 新增 | esbuild + 双 target |

**一句话**：这不是「重写游戏」，是「换壳 + 换 UI 层」。核心资产（模拟、纸感绘制、内容）都能留下。

## 3. 平台路径对比

| 路径 | 做法 | 代码复用 | 主要代价 | 结论 |
|---|---|---|---|---|
| **A. 小游戏 + 原生 Canvas + 适配层** | `game.js` 启动，`wx.createCanvas()` 上屏，重写 UI/输入/存储 | **60–75%** | UI 层重写约 1500–2000 行 | ✅ **推荐** |
| B. 普通小程序 + `<canvas type="2d">` + WXML UI | UI 用 WXML/WXSS，逻辑复用 | 逻辑 80% | 游戏类目违规，审核驳回/下架风险 | ❌ 不推荐 |
| C. 普通小程序 + `web-view` 套壳 | 直接加载现有 `index.html` | 90–95% | 个人主体不可用；需业务域名备案；审核认定「简单封装」；横屏/全屏/支付受限 | ⚠️ 仅内部演示 |
| D. Cocos Creator / LayaAir 重写 | 场景树 + 引擎 UI | 逻辑 40–60% | 22 个绘制函数全部改写；引擎包体 1–2MB；学习成本 | ⚠️ 仅多端战略时考虑 |
| E. Unity WebGL → 小游戏 | 引擎转换 | 低 | 包体、内存、启动时间都不合适 | ❌ |

### 3.1 为什么推荐 A 而不是引擎

- 现有绘制是**过程式 Canvas 路径**（`moveTo/lineTo/arc/gradient`），不是精灵图/场景树。Cocos 的 `Graphics` 虽然 API 相似，但坐标、层级、相机、资源管线都要重搭，等于把美术层重写一遍。
- 当前整包 159KB，小游戏主包上限 4MB，**没有任何包体压力**，引擎带来的「资源管理」收益为零。
- 游戏没有物理、骨骼动画、粒子系统（现有粒子是手写的），引擎的核心能力用不上。
- 何时该换引擎：如果后续要做多端（抖音/QQ/原生 App）、复杂动画、可视化关卡编辑，再评估 Cocos；那时也建议新项目用引擎，而不是回迁这个代码库。

### 3.2 如果一定要普通小程序

只有一种相对合理的做法：`<canvas type="2d">` 负责游戏画面，WXML 负责面板。逻辑复用率能到 80%，但：

- 微信要求游戏内容走小游戏类目，普通小程序做游戏属于类目不符；
- 小游戏的能力（虚拟支付、广告组件、开放数据域、分享卡片）在普通小程序里要么没有，要么形态不同；
- 一旦被判定类目不符，前期的 UI 工作全部作废。

所以不建议把它作为主路径，最多用于内部演示。

## 4. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | JavaScript（ES2019）+ JSDoc / `// @ts-check` | 现有 4274 行 JS，一次性迁 TS 不划算；核心模块用 JSDoc 获得类型检查 |
| 构建 | **esbuild**（双 target）+ **Vite**（Web 开发与单文件打包） | esbuild 快、配置少；`vite-plugin-singlefile` 保留「双击即玩」 |
| 渲染 | **原生 Canvas 2D** | 22 个绘制函数直接复用；小游戏原生支持 |
| 离屏画布 | `wx.createOffscreenCanvas({type:'2d'})`（基础库 ≥ 2.16.1） | 复用现有 `paper` / `house` 缓存思路 |
| UI | 自建 Canvas UI kit（约 600 行） | 小游戏无 DOM；不引入重型 UI 框架 |
| 输入 | 抽象为 action（`left/right/up/down/jump/interact/menu`） | 键鼠与触屏解耦，游戏逻辑不读键盘 |
| 状态 | 普通对象 + 显式存档 schema | 现有 `S` 结构够用，不需要 Redux |
| 存储 | KV 适配层 | Web `localStorage` / 小游戏 `wx.*Storage` |
| 云端 | **微信云开发**（云函数 + 云数据库） | 免域名备案、免登录态换取、按量计费 |
| 测试 | Vitest（core + 存档 fixtures）、Playwright（Web 截图回归）、微信开发者工具 + 真机 | 存档迁移必须有固定样本 |
| CI | `miniprogram-ci`（`type: 'miniGame'`） | 官方支持小游戏上传/预览 |
| 监控 | `wx.onError` / `wx.onUnhandledRejection` + 自建上报 | 小游戏线上排错必需 |

> 不建议引入 PixiJS / Phaser：它们替换的是渲染管线，而现有渲染恰好是最值得保留的部分。

### 5.2 平台适配层

先定义接口，再写两端实现。核心与渲染层**只认接口，不认 `wx` 或 `localStorage`**。

```js
// packages/platform/types.js
export const Platform = {
  kind: 'web',                       // 'web' | 'wx'
  canvas: {
    main: null,                      // 上屏 canvas
    dpr: 1,
    width: 1280,
    height: 720,
    safeArea: { top: 0, left: 0, right: 0, bottom: 0 },
    createOffscreen(w, h) {}         // 返回 { canvas, ctx }
  },
  raf(fn) {},
  now() {},
  setTimer(fn, ms) {},
  clearTimer(id) {},
  storage: {
    get(key) {},                     // 同步读，失败返回 null
    set(key, value) {},              // 异步写，用于常规保存
    setSync(key, value) {},          // 同步写，用于 onHide
    remove(key) {},
    info() {}                        // { currentSize, limitSize }，单位 KB
  },
  input: { onAction(fn) {} },        // fn({type:'down'|'up', action:'interact'})
  lifecycle: { onHide(fn) {}, onShow(fn) {}, onError(fn) {} },
  launchQuery: {},                   // Web 的 URL 参数 / 小游戏的 query
  share: { enable() {}, share(payload) {} },
  cloud: null                        // Web 为 null，小游戏为 wx.cloud 封装
};
```

Web 与小游戏两端的实现差异集中在这一个文件里，游戏代码里不再出现 `document`、`window`、`wx`。

小游戏侧的启动壳大约只有几十行，核心是三件事：拿上屏 canvas、按屏幕与 DPR 设尺寸、把触摸映射成 action。

```js
// apps/minigame/game.js
const canvas = wx.createCanvas();                 // 第一次调用返回上屏 canvas
const ctx = canvas.getContext('2d');
const win = wx.getWindowInfo();                   // 新 API，替代 getSystemInfoSync

const dpr = Math.min(2, win.pixelRatio || 1);
canvas.width = win.screenWidth * dpr;
canvas.height = win.screenHeight * dpr;

// 逻辑仍是 1280×720，letterbox 到屏幕
function fit() {
  const scale = Math.min(canvas.width / 1280, canvas.height / 720);
  const ox = (canvas.width - 1280 * scale) / 2;
  const oy = (canvas.height - 720 * scale) / 2;
  ctx.setTransform(scale, 0, 0, scale, ox, oy);
}

wx.onTouchStart(e => input.handleTouch('start', e.touches[0]));
wx.onTouchMove (e => input.handleTouch('move',  e.touches[0]));
wx.onTouchEnd  (e => input.handleTouch('end',   e.changedTouches[0]));
```

> 注意：小游戏没有 `window`，全局对象是 `GameGlobal`。如果引入第三方库需要 `window`，可以用官方 `weapp-adapter` 做 shim；但**不要指望它能把 DOM UI 跑起来**，它只补 BOM/事件等基础对象，不实现 HTML 布局与 CSS。

### 5.4 UI 层：三条路线，选 B

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 两端都改 Canvas UI | Web 丢掉现有 DOM/CSS，全部 Canvas 绘制 | 真正一套 UI | Web 现有纸感质感要重做，初期成本最高 |
| **B. 描述与渲染分离** | `ui/spec` 输出 `{title, lines, buttons, list}`；Web 用 DOM 渲染，小游戏用 Canvas kit 渲染 | 保留 Web 现有观感；交互逻辑只写一份 | 两个渲染器，需截图回归防漂移 |
| C. 小游戏单独写 UI | Web 完全不动 | 上手最快 | 两套 UI 各自演化，三个月后必漂移 |

**推荐 B**。现有界面本质上是「纸面板 + 标题 + 若干行文字 + 按钮 + 列表」，非常适合描述化：

```js
// packages/ui/spec/char.js
export function charPanel(state) {
  return {
    kind: 'panel',
    title: '人物',
    subtitle: `${state.age} 岁 · 第 ${state.week} 周`,
    sections: [
      { type: 'kv', rows: [
        ['体格', state.growth.body],
        ['心智', state.growth.mind],
        ['人缘', state.growth.charm]
      ]},
      { type: 'list', items: skillRows(state) }
    ],
    buttons: [
      { label: '知道了', action: 'close' }
    ]
  };
}
```

- Web 渲染器：把 spec 转成现有 `.paper` 结构，复用 CSS 与动画。
- 小游戏渲染器：Canvas 画圆角纸面板、文字自动换行、按钮命中检测、列表滚动。
- 好处：新增一个界面只写 spec；两端同时得到。

两个容易低估的细节：

- **纸感**：现有 `.paper` 的重复线性渐变、内阴影、四角折标，Canvas 都能画，但要手写；建议抽成 `drawPaper(ctx, rect)` 一次做好。
- **序章动画**：现有 CSS 的 `filter: blur()` 入场在 Canvas 里没有稳定等价物（`ctx.filter` 在小游戏支持不一致）。建议改成「透明度 + 位移 + 逐字延迟」，或用 2–3 层偏移绘制模拟模糊；不要在这里追求和 Web 完全一致。

Canvas UI kit 的最小能力集：面板、标题、正文换行、按钮（含禁用态）、键值行、列表（滚动/裁剪）、进度条、淡入淡出、toast。约 600–800 行。

### 5.5 输入：不要照搬键盘

| 行为 | Web | 小游戏 |
|---|---|---|
| 左右走 | A/D 或 ←/→ | 左下虚拟摇杆，或左右两个大按钮 |
| 上下楼 | W/S 或 ↑/↓ | 摇杆上/下；靠近梯子时自动提示 |
| 跳 | 空格 | 右下「跳」按钮 |
| 互动 | E | 右下主按钮，按最近物件显示「睡觉」「画画」「聊聊」 |
| 布置 | B | 右上菜单 → 布置；点家具选中，点位置放置，确认/取消 |
| 人物/帮助 | C / H | 右上菜单 |
| 关闭 | Esc | 面板右上「×」+ 系统返回 |

实现要点：

- 把 `keys` 布尔表抽象成 `input.axis = {x, y}` 与 `input.pressed(action)`，`updatePlayer()` 只读 abstraction。
- 触屏没有 hover：`getNear()` 的结果要**常驻显示**为按钮文案，而不是等玩家按键。
- 直接点家具触发交互（可选）比「走过去再按 E」更适合手机；但会削弱空间感，建议保留「走近 + 主按钮」，点击家具只做高亮。
- 布置模式必须改：鼠标右键删除在触屏不存在，改成「选中 → 底部删除按钮」。
- 安全区：横屏刘海机型，UI 内缩 `safeArea.left/right`。

### 5.6 渲染与性能

小游戏的 Canvas 2D 在 iOS 上通常没问题，中低端 Android 是瓶颈。现有代码有几处需要提前处理：

1. **分辨率**：逻辑仍是 1280×720，但上屏 canvas 用 `screenWidth × screenHeight × dpr`，通过 `translate/scale` 做 letterbox，不要把 canvas 直接设成 1280×720 拉伸。
2. **DPR**：`min(2, pixelRatio)`；`benchmarkLevel < 20` 的 Android 降到 1.25 或 1。
3. **静态层缓存**：`paper`、`house` 已经缓存，保持「换房/换场景才重绘」；小游戏里用 `wx.createOffscreenCanvas`，尺寸保持 1280×720，不要按 DPR 放大，否则两张图就吃掉 30MB。
4. **渐变与阴影**：每帧 `createLinearGradient` / `shadowBlur` 是主要开销。渐变对象缓存到模块级；阴影改成预渲染的模糊贴图。
5. **HUD**：现有 `updateHUD()` 每帧写 DOM；Canvas 版应缓存上次数值，只在变化时重绘，避免每帧 `measureText`。
6. **固定步长**：现在 `update(dt)` 把 `dt` 截到 0.05，掉帧时游戏时间会变慢。改成 1/60 固定步长 + accumulator，保证不同机型速度一致。
7. **内存**：`wx.onMemoryWarning` 时释放离屏缓存；常驻离屏画布控制在 2–3 张。
8. **兜底**：低端机可降到 30fps，但逻辑仍按固定步长推进。

### 5.7 构建产物

```bash
npm run build:web   # → dist/web/index.html（单文件，约 160KB）
npm run build:mini  # → dist/mini/{game.js, game.json, project.config.json}
npm run dev:mini    # 浏览器内模拟小游戏环境（触屏 + wx storage shim）
```

- `build:web` 继续产出单文件，保留「双击即玩」。

- `project.config.json`：`compileType: "game"`、`appid`、`setting.es6: true`。

## 6. 两版共存与统一维护

### 6.1 单一来源，不做 fork

最容易失败的做法是「复制一份 index.html 改成小游戏版」。三个月后两边的数值、文案、事件表就会不一致。正确做法是：

- **内容单一来源**：`content/` 下的房屋、场景、家具、出身、变故、剧情，两端构建时各自 import。
- **逻辑单一来源**：`core/` 不含任何平台 API；用 ESLint `no-restricted-globals` 禁掉 `document`、`window`、`wx`、`localStorage`。
- **界面单一来源**：`ui/spec/` 描述，两端渲染。
- **存档单一来源**：一份 schema、一份 migration，两端共用。

### 6.2 版本契约

| 字段 | 作用 | 规则 |
|---|---|---|
| `game` | 内容/规则版本，如 `4.2.0` | 仅提示，不阻断加载 |
| `schema` | 存档结构版本，整数 | **只增不改**；加载时严格比较 |
| `minClient` | 能打开此档的最低客户端版本 | 低于则提示升级，不尝试加载 |
| `platform` | `web` / `wx` | 仅用于统计与排错 |

规则：

- 新增字段：旧客户端忽略，新客户端给默认值；
- 删除/重命名字段：必须走 migration，不能直接删；
- 新客户端写出的档，旧客户端遇到 `schema > CURRENT` 时**拒绝加载并提示升级**，绝不「尽力解析」；
- 旧客户端读到新字段时保留在 `state._unknown`，保存时原样带回，避免降级破坏数据。

### 6.3 发布节奏

- Web：随时发，作为「设计试验场」，新玩法先在这里验证。
- 小游戏：提审 1–7 天（含驳回修改），版本通常落后 Web 一个 minor。
- 因此：**小游戏必须能打开上一版 Web 写的存档**；反向不要求（Web 读到未来版本时提示升级即可）。
- 分支：trunk-based，`main` 共享；发布打 tag `web-v4.2.0` / `mini-v4.1.3`；紧急修复 cherry-pick 到发布分支。

### 6.4 防漂移的工程手段

1. **存档 fixtures**：`tests/saves/` 放 v1 单档、v2 三档、v3 云档、损坏档、未来版本档；每次 CI 全跑。
2. **截图回归**：Playwright 对 Web 的 12 个界面截图；小游戏用开发者工具截图 + 真机抽查，关键界面人工比对。
3. **共享调试参数**：`?skip=1`、`?age=25` 等继续保留；小游戏侧用 `wx.getLaunchOptionsSync().query` + 开发者工具「编译模式」。
4. **平台差异白名单**：只允许在 `platform/` 和 `ui/*-renderer` 里写平台分支；`core/render` 里出现平台判断视为 code smell。
5. **同一份数值表**：`content/balance.js` 两端共用，调数值只改一处。

### 6.5 可接受的差异

| 差异 | Web | 小游戏 |
|---|---|---|
| 操作 | 键鼠 | 触屏 |
| 界面尺寸 | 16:9 自适应 | 全面屏 + 安全区 |
| 字体 | PingFang / 系统字体 | 系统字体，字号略大 |
| 分享 | 复制链接 | 微信分享卡片 |
| 音频 | 暂无 | 暂无（后续 `wx.createInnerAudioContext`） |
| 性能档位 | 固定 DPR 2 | 按 `benchmarkLevel` 降档 |

这些差异应由 `platform.features` 显式声明，而不是散落在业务代码里。

## 7. 存档设计

这是整个移植里最值得认真设计的一块。现有实现能用，但缺三样东西：**版本契约、容错、跨端通道**。

### 7.1 现状与问题

```js
// index.html:930
const SLOT_KEY = i => 'fusheng_slot_' + i;

// index.html:4030
function save(){
  const data = { v:2, slot:S.slot, /* ...20 多个字段... */, ts: Date.now() };
  localStorage.setItem(SLOT_KEY(S.slot), JSON.stringify(data));
}

// index.html:4046
function loadSave(d){ /* 逐字段赋值，未知字段被丢弃 */ }
```

问题：

1. `v` 只是数字，没有 migration 框架；v1→v2 靠一次性特判（`4491`）。
2. 没有校验，JSON 损坏或字段类型错误会直接把游戏带进异常状态。
3. 没有备份，写坏一次就丢档。
4. 没有云同步，换机/清缓存即丢失。
5. `speed` 等设备偏好混在存档里，跨端同步会互相覆盖。
6. `loadSave` 逐字段重建，未知字段丢失，旧客户端打开新档会「降级破坏」。
7. 每 15 秒写一次全量 JSON（`4517`），在手机上会有可感知的卡顿。

### 7.2 容量限制：先算清楚，再决定要不要优化

| 介质 | 限制 | 说明 |
|---|---|---|
| 小游戏 `Storage` | **10MB / 用户 / 小游戏** | 同一微信用户、同一个小游戏共享 |
| 小游戏单 key | **1MB** | 超过会写入失败 |
| 小游戏加密存储 | 7.1MB / 单 key 0.7MB | `encrypt: true` 时数据膨胀 1.4 倍 |
| 小游戏本地文件 | 约 200MB（用户目录） | 放导出文件/截图，不放存档 |
| Web `localStorage` | 约 5MB / origin | 各浏览器略有差异 |
| 云开发基础套餐 | 2GB 容量 + 20 万次调用/月 | 19.9 元/月，以控制台为准 |

**实测当前单档体积**：按 16 件家具、18 个剧情标记、3 个任务、完整角色与出身数据构造，JSON 约 **1.9KB**。3 个槽位约 **6KB**，占 10MB 的 **0.06%**。

结论：

- **不要为容量做分片、压缩、二进制序列化**，纯属过度设计。
- 单档设一个 64KB 的硬上限做保护即可（超过说明有 bug，比如把日志写进了存档）。
- 真正的约束是**写入频率**与**云调用次数**，见 7.5、7.6。

### 7.3 本地 vs 云端：本地优先，云端只做备份

| 维度 | 纯本地 | 本地 + 云备份（推荐） | 全云 |
|---|---|---|---|
| 离线可玩 | ✅ | ✅ | ❌ |
| 换机/重装恢复 | ❌ | ✅ | ✅ |
| 读档延迟 | 0 | 0（本地） | 网络往返 |
| 成本 | 0 | 19.9 元/月起 | 更高 |
| 冲突处理 | 不需要 | 需要 | 需要 |
| 合规 | 最简单 | 需隐私指引、数据删除入口 | 同 |
| 主要风险 | 清缓存/换机丢档 | 冲突覆盖 | 断网不可玩 |

**推荐：本地是唯一事实来源，云端是备份与迁移通道。**

- 游戏 tick 绝不读写网络；
- 启动先读本地，云端在后台拉取并比较；
- 只有「生日/搬家/传承/手动/切后台」才触发上传，且做节流（日终只在本地保存，不必然上云）；
- 断网时一切照常，待上传队列（outbox）下次补传。

设计说明：

- `saveId` 是跨端主键，`slot` 只是本地展示位。云端按 `saveId` 存，不按槽位，换端后槽位可以不同。
- `meta` 是列表页摘要，避免为了显示「23 岁 · 第 17 周 · 存款 1286」而解析全量 `state`。
- `revision` 每次写入 +1，用作云同步的乐观锁。
- `checksum` 用 FNV-1a 对 `state` 序列化结果取哈希，**只防损坏，不防作弊**（客户端可以重算）。
- `state._unknown` 保留旧客户端不认识的新字段，防止降级丢数据。
- `settings`（速度、音量、字号、减少动效）**不放进存档**，单独一个 key，不同步。

存储 key：

```
fs.meta             # 槽位索引 + 摘要
fs.slot.1           # 完整存档
fs.slot.1.bak       # 上一版，双缓冲
fs.settings         # 设备偏好，不同步
fs.migrations       # 已执行的迁移 id
fs.outbox           # 待上传队列（离线）
```

### 7.5 写入策略与容错

```js
// packages/core/save/store.js
const SCHEMA = 3;

export async function persist(storage, slot, state, { sync = false } = {}) {
  const key = `fs.slot.${slot}`;
  const prev = storage.get(key);
  const next = buildSave(slot, state, prev);

  if (prev) storage.setSync(`${key}.bak`, prev);   // 先留后路
  if (sync) storage.setSync(key, next);            // onHide 用同步
  else storage.set(key, next);                     // 常规保存用异步

  const meta = upsertMeta(slot, next);
  if (sync) storage.setSync('fs.meta', meta);
  else storage.set('fs.meta', meta);
}
```

规则：

- **触发点**：30 秒定时、日终、生日、搬家、传承、手动保存、`onHide`。
- `onHide` 必须用 `wx.setStorageSync`，异步写在切后台时可能被截断。
- **双缓冲**：写主 key 前先把上一版写到 `.bak`；启动时主 key 解析失败则回退 `.bak`。
- **校验**：读取时先 `JSON.parse`，再校验 `schema`、必需字段类型、`checksum`；任一失败走备份或提示「存档损坏」，不把异常状态带进游戏。
- **迁移**：串行执行，每步成功才写下一次；迁移前自动备份；失败保留原档。
- **启动性能**：启动只读 `fs.meta`，选中槽位后再懒加载完整存档，避免启动时多次同步读。

```js
// packages/core/save/migrate.js
const MIGRATIONS = {
  1: d => ({ ...d, schema: 2, slot: d.slot || 1 }),
  2: d => ({
    ...d,
    schema: 3,
    saveId: d.saveId || uid(),
    meta: buildMeta(d),
    state: pickState(d),
    settings: undefined
  })
};

export function migrate(raw) {
  let d = raw;
  while ((d.schema || 1) < SCHEMA) {
    const step = MIGRATIONS[d.schema || 1];
    if (!step) throw new SaveError('NO_MIGRATION');
    d = step(d);
  }
  if (d.schema > SCHEMA) throw new SaveError('SAVE_TOO_NEW');
  return d;
}
```

### 7.6 云同步：什么时候传，比传什么更重要

**不要每次自动保存都上云。** 算一笔账（按当前 1 秒 = 12 游戏分钟）：

- 云开发基础套餐含 **20 万次调用/月**；
- 1 游戏日 = 1440 游戏分钟 = **2 分钟真实时间**；30 分钟一局 ≈ 15 个游戏日 ≈ **2 次生日**；
- 一次同步 = 1 次云函数 + 1 次数据库写 ≈ **2 次调用**；
- 若每个日终都同步：`1000 DAU × 15 次/天 × 30 天 = 45 万次同步/月`，约 **90 万次调用**，超配额 4 倍以上；
- 改成「生日/搬家/传承/手动/切后台（节流 5 分钟）」：约 `2–3 次/局` → `6–9 万次同步/月` → **12–18 万次调用**，勉强在 20 万以内。

结论：**1000 DAU 就是基础套餐的边缘**。再往上要么调低同步频率、只让付费/登录用户开云同步，要么自建（一台轻量服务器 + SQLite/Postgres 的成本远低于按次计费）。这也是 7.5 里「日终只本地保存」的原因。

同步协议：

```
pull(saveId)                    -> { revision, state, updatedAt }
push(saveId, baseRevision, state)
  if baseRevision < server.revision -> 409 + 服务器版本
  else                              -> 写入, revision + 1
list()                          -> [{ saveId, meta, revision, updatedAt }]
delete(saveId)                  -> tombstone { deleted: true, deletedAt }
```

冲突处理：

- **绝不自动覆盖**。模拟状态无法安全合并，自动 merge 会造出「年龄 23、周数 30」这种脏档。
- 收到 409 时弹对比卡：本机（年龄/周/存款/更新时间）vs 云端（同字段），让玩家选。
- 落选的那份写入 `conflict` 备份槽，不直接删。
- 删除用 tombstone，保留 30 天，避免另一台设备把已删档「复活」。
- `updatedAt` 以服务端时间为准，客户端时间只用于显示。

身份：

- 小游戏：`wx.login` 拿 code，云函数里 `cloud.getWXContext().OPENID`，不需要自己维护登录态。
- Web：没有 openid，用「同步码」把两端绑定（见 7.7）。

安全边界：

- 客户端存档天然可篡改，`checksum` 不是防作弊；
- 如果以后接内购/广告奖励，**权益必须服务端记账**，不能放在存档的 `money` 或 `unlocked` 字段里；
- 云数据库权限设为「仅创建者可读写」，写入走云函数以校验 `revision` 与 `openid`。

### 7.7 Web ↔ 小游戏：兼容与迁移

两端本地存储是隔离的（不同沙箱），不能直接读对方的 key。四种通道：

| 方式 | 体验 | 需要后端 | 适用 |
|---|---|---|---|
| **云同步码** | 最好：Web 生成 8 位码 + 6 位 PIN，24 小时有效；小游戏输入即拉取 | 是 | 推荐 |
| **剪贴板存档码** | 好：`FS1.` + LZ-string(JSON) + `.` + checksum；复制粘贴 | 否 | 零后端首选 |
| 文件导出 | 一般：Web 下载 `.fsave`；小游戏侧导入受文件选择 API 限制 | 否 | 备份用途 |
| 二维码 | 一般：压缩后约 1.2KB，可编码但扫码链路繁琐 | 否 | 线下场景 |

推荐组合：**有云用同步码，没云用剪贴板码**。

同步码需要一个 Web 可访问的 HTTP 入口：云开发可以用 HTTP 访问服务 / 云托管，自建则用一台小服务器 + HTTPS 域名；小游戏侧走 `wx.cloud` 或 `wx.request`（后者需在后台配置 request 合法域名）。同步码本身只存 24 小时，过期即删，避免变成长期账号体系。

```js
// 导出：compressToEncodedURIComponent 的输出只含 A-Z a-z 0-9 + - $，不含分隔符
const sum  = fnv1a(JSON.stringify(save.state));
const body = LZ.compressToEncodedURIComponent(JSON.stringify(save));
const code = 'FS1.' + body + '.' + sum;

// 导入
const [tag, body2, sum2] = code.split('.');
if (tag !== 'FS1') throw new SaveError('BAD_FORMAT');
const save = JSON.parse(LZ.decompressFromEncodedURIComponent(body2));
if (fnv1a(JSON.stringify(save.state)) !== sum2) throw new SaveError('BAD_CHECKSUM');
const migrated = migrate(save);   // 统一走迁移
```

兼容规则：

1. **同 schema 才能直传**；`schema > CURRENT` 拒绝并提示升级；`schema < CURRENT` 先迁移。
2. **旧档统一走 migration**：Web v1 单档 → v2 三槽 → v3；小游戏只认 v3，导入时在内存里跑完整链路。
3. **未知内容降级**：`loadSave` 已有家具过滤（`FURN[f.t]`，`index.html:4058`），把同样的策略扩展到场景 id、事件 id、出身 id；未知项跳过并记一条 warning，不让整档失败。
4. **角色名/文本**：导入前做长度与敏感词校验；上传分享前走 `msgSecCheck`。
5. **回滚**：小游戏版本落后时，读到更高 `schema` 只提示「请更新微信版本」，不写回、不迁移、不删除。

迁移矩阵：

| 来源 | 目标 | 方式 |
|---|---|---|
| Web v1 单档 | Web v2 三槽 | 现有 `4491` 逻辑，启动时执行 |
| Web v2 | schema v3 | `MIGRATIONS[2]` |
| Web schema v3 | 小游戏 schema v3 | 云同步码 / 剪贴板码 |
| 小游戏 schema v3 | Web schema v3 | 同上，反向 |
| 任意未来版本 | 当前客户端 | 拒绝加载 + 提示升级 |

### 7.8 合规与隐私

- 存档含玩家输入的角色名，属于用户内容：上传/分享前做内容安全检测。
- 隐私指引需声明：openid、存档数据、设备信息、错误日志的收集与用途。
- 提供「删除云存档」入口；账号注销后 30 天内清理。
- 未成年人相关：按平台要求接入实名、防沉迷、适龄提示；有内购时这是硬门槛。

### 8.2 阶段划分

| 阶段 | 内容 | 产出 | 验收 |
|---|---|---|---|
| P0（2–3 天） | 抽 `platform` 接口；storage/input/lifecycle 先接 Web；存档升 v3 + fixtures | Web 行为不变，存档可迁移 | 旧档能读，新档能回读，fixtures 全绿 |
| P1（5–7 天） | 拆 `core/render/ui`；Web 单文件构建；Canvas UI kit + 3 个核心界面（标题/读档/HUD） | Web 版观感不变 | 截图对比无回归；单文件仍可双击 |
| P2（5–7 天） | 小游戏壳、横屏适配、触屏、剩余 9 个界面 | 真机跑通一局 7→30 岁 | 无 JS 报错；低端机 ≥ 30fps |

总量级：约 **20–30 个工作日**（不含审核等待）。其中 UI 重写占一半以上，是最大的不确定性。

## 9. 风险与取舍

| 风险 | 影响 | 应对 |
|---|---|---|
| UI 重写超预期 | 工期翻倍 | 先做 3 个界面验证 Canvas kit，再铺开；不要一开始就做 12 个 |
| 小游戏类目/资质 | 无法上线 | 先做个人免费版；内购后置，企业主体 + 版号提前规划 |
| 低端机性能 | 掉帧、发热 | DPR 降档、静态层缓存、30fps 兜底、真机矩阵 |
| 双端漂移 | 数值/文案不一致 | 单一 `content` + `core`；CI fixtures；截图回归 |
| 云调用超配额 | 额外费用/限流 | 同步节流；只在中点事件上传；规模化后自建 |
| 触屏手感 | 玩家流失 | 不照搬键盘；主按钮按情境换文案；真机试玩再定方案 |
| 存档冲突 | 丢进度 | 不自动合并；对比卡 + 落选备份 |
| 审核周期 | 版本滞后 Web | schema 向后兼容；小游戏可落后一个 minor |

**几个明确的取舍**：

1. **不做实时云存档**：单机游戏，本地优先，云端只备份。
2. **不做双端 UI 统一**：保留 Web 现有 DOM/CSS 观感，小游戏用 Canvas 重画；用 spec 约束结构，而不是强求像素一致。
3. **不引入游戏引擎**：现在换引擎是负收益；等多端战略明确再评估。
4. **不做存档压缩/分片**：1.9KB 的档，压缩省不下任何有意义的空间，反而增加故障点。
5. **不在首版做内购**：个人主体 + 免费版能最快验证；版号与企业资质是另一条长线。

## 10. 小结

- **平台**：微信小游戏，不是普通小程序，也不是 web-view 套壳。
- **技术栈**：原生 Canvas 2D + esbuild/Vite + 自建 Canvas UI kit + 微信云开发；不引引擎。
- **架构**：`core / render / ui / platform` 四层，`web / minigame` 两个壳；逻辑与内容单一来源，UI 描述与渲染分离。
- **共存**：monorepo、同一份内容与存档 schema；Web 先行迭代，小游戏审核滞后但能读旧档；用 fixtures 与截图回归防漂移。
- **存档**：v3 schema（`saveId` / `revision` / `checksum` / `meta` / `_unknown`），本地优先、云端备份、双缓冲写入、串行迁移；容量不是问题（单档 1.9KB），云调用次数才是；Web↔小游戏用同步码/剪贴板码迁移，冲突不自动合并。
